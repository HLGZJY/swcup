# 项目协作规范 — 鼻纹智救

> 源自 Karpathy 启发，适配本竞赛项目的 AI 协作原则

---

## 四原则

| 原则 | 核心含义 |
|------|----------|
| **Think Before Coding** | 不假想、不隐藏困惑、不擅自做无依据假设 |
| **Simplicity First** | 用最少的代码解决问题，不超前设计 |
| **Surgical Changes** | 只改必须改的，不碰无关代码 |
| **Goal-Driven Execution** | 先定成功标准，再用验证循环推进 |

---

## 1. Think Before Coding

- **不擅自假设**：技术选型、接口设计等有歧义的地方，先提出方案再执行
- **主动提tradeoff**：当你发现两个方案各有权衡时，列出优劣让用户选择
- **困惑即停**：遇到模糊需求时说"我这里不清楚XX，请确认"，不等报错
- **本项目适用**：数据库表结构、API 设计、模型方案等在老师确认前不默认执行

---

## 2. Simplicity First

- **MVP思维**：先跑通核心流程（采集→比对→认领），不做扩展功能
- **不超前设计**：三层架构、依赖注入等，先看W2~W3实际需求再引入
- **代码量检查**：如果一个文件可以50行解决，不写100行
- **本项目适用**：后端 Node.js (Express) 不引入 TypeScript（降低复杂度），前端 UniApp 不引入状态管理库（Vue3 响应式足够）

---

## 3. Surgical Changes

- **最小改动**：只改任务直接相关的文件，不"顺手"优化无关代码
- **不删死代码**：别人写的、看起来无用但不确定的代码，只报告不动手
- **自己产生的废代码自己清**：如果你的改动导致某个变量/函数/import不再使用，清理它
- **匹配现有风格**：即使你更偏好另一种写法，改动时沿用项目已有风格

---

## 4. Goal-Driven Execution

- **任务转目标**：把"实现XX功能"变成"验证XX功能可正常运行"
- **分步骤 + 验证点**：每个步骤后写清楚如何验证（curl测试/页面操作/单元测试）
- **多步骤任务示例**：

```
1. 创建后端 Express 项目骨架 → 验证: npm start 可运行，返回空JSON
2. 编写宠物档案 CRUD API → 验证: POST /api/animals 返回201，GET /api/animals 返回数组
3. 前端调用 API 显示列表 → 验证: 页面加载后显示数据，无console.error
```

## 项目特定规则

### 文档读写
- 所有项目文档读写操作均在 `F:\课设与软件杯\AI 驱动的流浪动物防重复救助系统设计\` 下进行
- 每次对话先读取 `log.md` 最新记录，了解当前进度
- 改动文件后同步追加 `log.md` 操作记录

### 技术决策链
```
队长（你/AI助理）提出方案 → 用户确认 → 执行
```
重大决策（技术栈切换、架构变更）不在未告知情况下直接改动

### 代码协作（参考学姐项目）
- 前端 UniApp + Vue3：参考 `基于定位的流浪动物救助系统管理端微信小程序开发`
- AI 推理 FastAPI：参考 `ai防重复救助/pets-face-recognition`
- 不直接复用学姐项目的业务逻辑，只复用 UI 组件模式

### Git 规范
- commit message 格式：`[日期] 类型 | 摘要`
- 类型：feat / fix / refactor / docs / wip
- 未完成的改动不 commit，用 `[wip]` 标记

### 量化门控（参考 milestone）
- W3 前 baseline 模型 Accuracy ≥ 70%
- W4 前 融合召回率 ≥ 80%，响应时间 < 2秒
- 不在未达到门控前跳过阶段

## 何时严格 / 何时灵活

| 场景 | 原则 |
|------|------|
| 技术选型、架构变更 | 严格：先方案后执行 |
| typo、简单单行修改 | 灵活：直接改 |
| 新增 API 接口 | 严格：先定义接口文档再写代码 |
| 改现有 bug | 严格：先写复现步骤/测试再修复 |
| 文档更新（无歧义） | 灵活：直接改 |

---

## 成功标志

符合规范的协作应体现：
- diff 只包含必要的改动
- 技术决策前有方案说明
- 每次改动后 log.md 有记录
- 重大变更前有用户确认环节
