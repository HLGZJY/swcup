## 产品定义

### 产品名称

**"鼻纹智救"** — AI 流浪动物精准救助平台

（备选：寻它、救助智联）

### 一句话定位

> "通过自训练轻量化 AI 模型 + 四维度融合查重，用手机拍一下狗鼻子，2 秒内告诉你这只狗是否已被救助过，大幅减少重复劳动。"

### 目标用户

| 用户角色 | 描述 | 典型场景 |
|----------|------|----------|
| 普通救助者 | 发现流浪动物的个人，希望快速确认是否已被救助 | 发现流浪猫→上传鼻纹→AI检测→避免重复行动 |
| 救助站/民间组织 | 需要协调资源，避免重复救助 | 接收动物→查询是否重复→合并档案 |
| 动物保护协会 | 监管流浪动物数据，统计分析 | 查看重复率趋势→优化资源分配 |

### 核心用户故事

**救助者视角：**
> "我发现一只流浪猫，想发布求助。但系统告诉我，这只猫 3 天前已在 500 米外被报告过。我选择联系原救助者，而不是重复行动。"

**管理员视角：**
> "系统 AI 提示两条留言高度相似（特征相似度 95%，定位相距 200 米），我一键合并，避免信息重复。"

## 核心问题

### 重复救助：一个被长期忽视的系统性问题

流浪动物救助面临的核心问题是**重复救助**。

一只走失的狗，被 A 救助者发现并发布 → 被 B 救助者在不同地点再次发现并发布 → 被 C 救助者第三次发布……同一条生命被重复投入医疗检查、重复安置、重复消耗志愿者时间。救助站之间无法互通信息，人工比对手机里的照片效率极低，大量重复信息石沉大海。

**具体表现**：

| 场景 | 现状 |
|------|------|
| 节假日走失高峰 | 同一只狗的寻主帖可在多个救助群出现 3~6 次 |
| 人工比对一条记录 | 耗时 5~15 分钟，且依赖主观判断，容易出错 |
| 救助站日常 | 工作人员反映"同一只狗被不同人送来好几次"极为常见 |
| 商业 API 调用 | 单次成本约 0.5~2 元，且不支持流浪动物个体识别 |

> 数据来源：基于国内救助站访谈及一线救助人员反馈，非权威统计，仅供参考。

### 传统解法的局限

| 方案 | 效果 | 局限 |
|------|------|------|
| 人工比对照片 | 主观、准确率低 | 效率低、无法规模化 |
| 微信群/朋友圈转发 | 依赖社交网络 | 信息孤岛、无法查重 |
| 商业鼻纹 API（百度/旷视） | 支持个体识别 | 成本高、调用限制、不适合中国流浪动物场景 |

现有商业方案均无法直接满足"低成本、高准确率、面向流浪动物特化"的需求，这正是本项目的切入点。

## 项目目标

### 产品角度：一句话说清楚

> **"用手机拍一下狗鼻子，AI 在 2 秒内告诉你这只狗是否已经被救助过。"**

这是一个面向普通救助者的"即拍即查"工具：不需要任何专业知识，不需要额外硬件，只需一部手机。

### 技术角度：怎么做

1. **采集阶段**：用户拍摄狗鼻纹照片 → AI 活体检测（判断是真实狗鼻而非照片）→ 提取鼻纹特征向量（512维）
2. **比对阶段**：新向量与数据库中的历史档案做四维度融合比对（鼻纹特征 40% + GPS 位置 20% + 整图相似度 20% + 文本描述 20%）→ 加权得分返回 Top-N 结果
3. **认领阶段**：用户确认是否认领 → 状态流转（走丢 → 已找到 → 已认领 → 已归档）

### 量化目标

| 指标 | W3 Baseline | W4 质量门控 |
|------|-------------|-------------|
| 鼻纹识别 Top-1 准确率 | ≥ 70% | ≥ 85% |
| 融合查重综合召回率 | — | ≥ 80% |
| 单次比对响应时间 | — | < 2 秒 |
| 系统可用性 | 前端可运行 | 端到端可联调 |

### 技术创新点

1. **轻量化自训练模型**：不依赖商业 API，0 成本实现个体识别（MobileNetV2 + ArcFace 度量学习）
2. **多维度融合查重**：单一鼻纹比对 → 四维度综合判断（特征+鼻纹+定位+图片），降低误报率
3. **面向移动端优化**：512 维向量，CPU 可推理，无需 GPU 服务器

### 核心创新亮点

| 维度 | 传统方案 | 本项目 |
|------|----------|--------|
| 重复检测 | 人工比对，靠眼睛 | AI 多维度综合判断（特征+鼻纹+定位+图片） |
| 技术路线 | 调用商业 API，成本高/不支持个体识别 | 轻量化自训练模型，0 成本，支持个体识别 |
| 准确性 | 低，受主观影响大 | 高，客观可量化（余弦相似度） |
| 定位方式 | 无 | GPS 位置辅助判断，减少误报 |
| 响应速度 | 人工 5~15 分钟/次 | AI < 2 秒/次 |

### 技术创新点

1. **轻量化自训练模型**：不依赖商业API，0成本实现个体识别
2. **多维度融合查重**：特征向量 + 鼻纹 + GPS + 图像 + 文本综合判断
3. **迁移学习应用**：用开源数据集 + 少量自采数据达到 90%+ 准确率

## 系统架构

### 技术选型

||| 层级    | 技术选型                       | 说明                    |
||| ----- | -------------------------- | --------------------- |
||| 用户端   | 微信小程序 + UniApp + Vue3      | 普通救助者使用，即用即走        |
||| 管理端   | 微信小程序 + UniApp + Vue3      | 管理员使用，独立入口          |
||| 后端    | Node.js (NestJS) + MySQL  | RESTful API，TypeScript，TypeORM |
||| AI 推理 | FastAPI + PyTorch          | Python 直调模型，接口开发快     |
||| AI 模型 | MobileNetV2 迁移学习           | 512维向量，CPU 可推理        |
||| 向量存储 | MySQL BLOB（初期）/ pgvector（后期） | 鼻纹向量直接存 MySQL，降低复杂度   |

> **技术栈切换记录**：原计划用 Spring Boot + MySQL（W1 原定），因开发效率及团队技术匹配考量，切换为 Node.js (NestJS) + MySQL。

### 系统调用链路

```
用户端小程序                    管理端小程序
     │                              │
     └────────── RESTful API ───────┘
                     │
          ┌──────────┴──────────┐
          │                     │
    Node.js 后端              FastAPI 推理服务
    (Express)                  (Python/PyTorch)
          │                     │
          └──────────┬──────────┘
                     │
              MySQL 数据库
        (档案 + 事件 + 鼻纹向量)
```

> **架构说明**：后端与 AI 推理服务独立部署，通过内部 HTTP 通信。AI 服务不暴露公网，仅后端可调用。
