## 1. 概述

本项目使用 MySQL 8.0 存储，TypeORM 0.3.29 作为 ORM（基线 #6，`backend/package.json:42`）。

**重要更正**：项目实际有 **5 张表**（不是历史 spec 写的 6 张）。`locations` 不是独立表，位置坐标直接嵌入在 `animals` 和 `rescue_events` 表中。基线 #11。

| 表名 | 实体类 | 来源 |
|------|--------|------|
| `users` | `User` | `backend/src/users/entities/user.entity.ts` |
| `animals` | `Animal` | `backend/src/animals/entities/animal.entity.ts` |
| `nose_features` | `NoseFeature` | `backend/src/nose/entities/nose-feature.entity.ts` |
| `rescue_events` | `RescueEvent` | `backend/src/events/entities/event.entity.ts` |
| `claims` | `Claim` | `backend/src/claims/entities/claim.entity.ts` |

注册位置：`backend/src/app.module.ts:44` `entities: [User, Animal, NoseFeature, RescueEvent, Claim]`

**关键配置**：
- 字符集：`utf8mb4`（支持 emoji）
- 存储引擎：`InnoDB`（事务 + 外键）
- 主键策略：UUID（`varchar(36)`，应用层 `uuid` 包生成）
- 自动同步：`synchronize: true`（开发期自动建表，**生产环境应关闭**）

**DDL**：
```sql
CREATE TABLE `nose_features` (
  `vector_id` varchar(36) NOT NULL,
  `animal_id` varchar(36) DEFAULT NULL,
  `feature_vector` text NOT NULL,  -- 1024 hex chars = 512 bytes Float32
  `vector_dimension` int NOT NULL DEFAULT 512,
  `nose_photo_url` varchar(255) NOT NULL,
  `body_photo_url` varchar(255) DEFAULT NULL,
  `landmark_data` json DEFAULT NULL,
  `confidence_score` decimal(5,4) DEFAULT NULL,
  `is_primary` tinyint(1) NOT NULL DEFAULT 0,
  `collection_angle` enum('front','left','right','top') NOT NULL DEFAULT 'front',
  `model_version` varchar(50) NOT NULL,
  `liveness_check_passed` tinyint(1) NOT NULL DEFAULT 0,
  `created_at` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`vector_id`),
  KEY `idx_animal` (`animal_id`),
  KEY `idx_created` (`created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**关键设计决策**：
1. **HEX 字符串存储向量**：每个 Float32 归一化到 [0, 1] → ×255 → 转 2 位 hex → 512 字符 ×2 = 1024 字符
   - 编码：`backend/src/nose/nose.service.ts:60-67` `encodeVector`
   - 解码：`backend/src/nose/nose.service.ts:69-77` `decodeVector`
   - **优势**：可读、可调试、跨平台
   - **代价**：存储比 BLOB 大 2 倍，比 Float32 Binary 大 4 倍
2. **`animal_id` 可空（孤儿鼻纹）**：用户采鼻纹但未建档前，animal_id 为 NULL
3. **Bug6 修复**（`animals.service.ts:72-82`）：建档时回填所有 `vector_id=dto.primary_nose_id AND animal_id IS NULL` 的孤儿
4. **未用专用向量库（如 pgvector）**：5000 条以内的数据规模，MySQL LIKE/全表扫已足够（实测响应 < 100ms）

## 4. 关键设计决策

### 4.1 鼻纹向量用 HEX 字符串而非 BLOB / 向量库

**决策**：用 `text` 列存 HEX 字符串
- **方案对比**：
  - 方案 A：BLOB 存 2048 字节 → 选 **BLOB**（紧凑），但不可读
  - 方案 B：HEX 字符串 1024 字符 → **采用此方案**（可读、跨平台）
  - 方案 C：pgvector 专用库 → 拒绝（运维成本高、规模小用不上）
- **结论**：HEX 方案在 5000 条数据内性能足够（实测 < 100ms），可读性更好

### 4.2 status 全部用 ENUM

**决策**：所有状态字段用 MySQL `enum` 而非 varchar+CHECK
- **优势**：
  - 写入时强校验（非法值直接报错）
  - 存储紧凑（1 字节）
  - 文档自带（DDL 即文档）
- **代价**：新增状态需要 ALTER TABLE

### 4.3 JSON 字段存扩展信息

**决策**：photos / tags / proof_photos / candidates 用 `json` 类型
- **优势**：前端传什么存什么，无需 DDL 变更
- **代价**：无强 schema，文档需显式说明结构（`candidates` 在 `event.entity.ts:113-114` 注释）

### 4.4 synchronize: true 的取舍

**决策**：开发期 `synchronize: true`（`app.module.ts:45`），生产环境应关闭
- **优势**：改 entity 后无需手动 ALTER
- **风险**：生产环境误开可能丢数据
- **推荐**：用 TypeORM Migrations 替代

## 5. 性能优化

| 索引 | 适用查询 | 来源 |
|------|----------|------|
| `idx_status_species` | `WHERE status='lost' AND species='dog'` | 列表/上报匹配 |
| `idx_location (lat, lng)` | `WHERE lat BETWEEN ? AND ?` | 5km 粗筛 |
| `idx_primary_nose` | `WHERE primary_nose_id = ?` | 鼻纹反查动物 |
| `idx_nose_vector` | `WHERE nose_vector_id = ?` | 事件反查鼻纹 |
| `idx_reporter` | `WHERE reporter_id = ?` | 我的事件 |
| `idx_status` (claims) | `WHERE status='pending'` | 待审批列表 |

**实测响应时间**（开发期）：
- 列表查询（20 条/页）：< 30ms
- 鼻纹匹配（含 1024 hex 解码 + 余弦相似度）：< 100ms（5000 条数据内）
