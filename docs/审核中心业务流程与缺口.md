# 审核中心业务流程与缺口

> 整理人：统筹协调者
> 日期：2026-05-21
> 背景：前端主体功能开发完毕，业务流程系统性梳理后，识别出审核中心核心缺口

---

## 一、业务流程定义

### 事件自动处理规则（用户上报时触发）

| 融合得分 | 系统行为 | 后续流向 |
|----------|----------|----------|
| ≥ 0.88 | 自动确认重复，自动合并到已有档案 | 无需管理员处理 |
| 0.75 ~ 0.88 | 标记疑似重复 | **管理员审核队列** |
| < 0.75 | 自动新建动物档案 | 无需管理员处理 |

> 到达管理员审核中心的事件 = 融合得分在 0.75~0.88 区间，系统拿不准的案例

### 三种操作的业务语义

| 操作 | 接口 | 业务含义 | 数据变化 |
|------|------|----------|----------|
| **process** | `POST /admin/events/:id/process` | 对字段缺失/比对失败的事件做AI识别，填充 species/breed，再重新发起比对 | rescue_events.status → `'identified'`，species/breed 被填充 |
| **confirm** | `PUT /admin/events/:id/confirm` | 管理员认可比对候选，确认这个动物已存在于档案中，合并到已有档案 | rescue_events.status → `'duplicated'`，is_duplicate → true |
| **reject** | `PUT /admin/events/:id/reject` | 比对结果有误或事件无效，驳回后事件结束 | rescue_events.status → `'rejected'` |

### 典型场景：张三的走失狗

1. **用户上报**：张三的狗走失，上传鼻纹照片 + 描述 → 系统自动比对 → 与王五的走失柴犬融合得分 0.81 → 事件 A 进入管理员审核队列（status=`pending`）
2. **管理员李四看到**：
   - 事件基本信息（描述/位置/时间）
   - **比对候选列表**（top-N 动物 + 4维度得分 + 融合得分）← 当前缺失
   - **候选动物档案卡片**（照片/品种/状态）← 当前缺失
3. **李四决策**：
   - 确认是同一只狗 → 点 **confirm**（需指定合并到哪个动物）→ 事件标记为重复
   - 比对错了 → 点 **reject** → 事件被驳回
   - 物种字段缺失 → 点 **process** → AI重新识别

## 二、缺口清单

### 缺口一：管理员看不到比对候选列表（🔴 P0）

**现象**：`GET /admin/events/:event_id` 只返回事件本身，没有返回比对候选数据。

**影响**：管理员只能看到一个数字，看不到对比的原始照片和候选动物档案，**无法做判断**——审核流程实质上不可用。

**根因代码**：
```typescript
// admin.service.ts:40-44
async getEventDetail(event_id: string) {
  const event = await this.eventRepo.findOne({ where: { event_id } });
  if (!event) throw new Error('Event not found');
  return event;  // ← 只有事件记录，没有任何比对候选信息
}
```

**需要的字段**：
```typescript
{
  event_id: "e001",
  status: "pending",
  // ... 事件本身字段
  candidates: [  // ← 需要新增
    {
      animal_id: "a001",
      fusion_score: 0.81,
      vector_similarity: 0.95,
      gps_distance_m: 320,
      image_similarity: 0.88,
      text_match_rate: 0.80,
      animal: {
        species: "dog", breed: "柴犬", color: "黄白",
        status: "lost", photos: [...], address: "朝阳区某街道"
      }
    },
    // ... more candidates
  ]
}
```

### 缺口二：confirm 操作没有记录合并目标（🔴 P0）

**现象**：管理员在审核详情页选中了候选列表里的某只动物，但 confirm 操作没有传 `animal_id`，这个选择没有被持久化。

**根因代码**：
```typescript
// admin.service.ts:46-48
async confirmEvent(event_id: string) {
  await this.eventRepo.update(
    { event_id },
    { status: 'duplicated' as any, is_duplicate: true }
  );
  // ↑ 没有 link 到任何 animal_id
}
```

**需要的改动**：
- 接口：`PUT /admin/events/:event_id/confirm` 增加 `animal_id` 请求体参数
- 写入：`rescue_events.animal_id` = 管理员选中的目标动物档案 ID

### 缺口三：前端审核详情页 UI（🟡 P1）

**现象**：前端审核详情页虽然有 confirm/reject/process 三个按钮，但**没有渲染候选列表的区域**。

**需要的 UI 组件**：
- 比对候选列表（top-N）
- 每个候选的融合得分 + 四维度得分明细
- 每个候选的动物档案卡片（照片/品种/颜色/状态）
- 管理员选中候选后触发 confirm

> 前端等后端接口就绪后接入，数据结构见缺口一。

## 三、接口改动要求

### `GET /admin/events/:event_id` — 增加候选列表

**当前返回**：事件记录本身

**需要返回**：事件记录 + `candidates[]`

**候选人数据来源**：该事件上报时触发的比对结果（应存储在 events 表或单独的比对记录表）

### `PUT /admin/events/:event_id/confirm` — 增加目标指定

**当前请求**：无参数（只打标签）

**需要请求**：
```json
{
  "animal_id": "a001"  // 管理员选中的合并目标动物档案
}
```

### `POST /admin/events/:event_id/process` — AI识别

**当前行为**：只更新 status 和 species/breed

**建议行为**：调用 FastAPI `/extract/feature` 获取向量 → 重新执行四维度融合比对 → 更新事件记录中的比对结果字段（使管理员可在详情页看到重新比对后的候选列表）
