# BUG-013 "采集"与"发现"流程标准不统一

**优先级**: 🟠 P1  
**标签**: `bug`, `architecture`, `workflow`, `product`  
**发现时间**: 2026-07-06  
**测试场景**: P4

---

## 现象

- **采集页(`/pages/collect`)**:用户提交后,动物档案直接出现在首页走失列表,**不走审核**
- **发现页(`/pages/find`)**:用户提交后,先进 admin 待审中心,审核员决定"驳回"或"确认合并"后才展示

两种"上报"动作的处理路径完全不同,产品逻辑混乱。

## 复现步骤

### 路径 A(采集页)
1. 采集页提交一只动物的全身照 + 鼻纹
2. → 创建档案 → 自动出现在首页走失列表
3. admin 端"事件审核"tab 出现对应事件(status=pending)

### 路径 B(发现页)
1. 发现页提交一只动物的发现信息(全身照 + GPS + 描述)
2. → 事件进入 admin"发现上报"待审页
3. admin 决定合并 / 驳回
4. → 合并后该动物 report_count +1

## 预期

两种入口应有**统一处理逻辑**:
- 一致的融合算法(参见 [BUG-006](BUG-006-nose-score-inconsistent.md))
- 一致的展示规则(都先审核,或都不审核)
- 都能产出"创建新动物"选项(参见 [BUG-014](BUG-014-admin-no-create-new.md))

## 实际

- 采集页直发首页,绕过审核
- 发现页走审核,且审核员只能"驳回/合并"无法"创建新动物"

## 用户原话

> "正常的逻辑是 该动物的事件进来 携带一些参数(位置 鼻纹 文本),再去和现有的动物的参数进行 相应的分数运算,得到相应的分数。这里的鼻纹相似度使用的算法应该与采集页面的鼻纹分数使用同一个。"
> "所以审核端的作用应该是审核用户的创建是否能展示在公共区域 跟前端的采集页面应使用同一套分数算法"

## 用户建议的修复方向

> "采集完全不走审核就能展示到公共区域,发现走审核是驳回还是合并 似乎也没有创建新动物的选项"
> "审核端的作用应该是审核用户的创建是否能展示在公共区域"

## 修复建议

### 方案 A:统一两个入口都走审核
- 采集页提交 → 进入 admin 事件审核 → 确认后展示
- 发现页维持现状
- 优点:管理可控
- 缺点:用户体验差(走失主人都要等审核)

### 方案 B:统一两个入口都不走审核(直发)
- 发现页提交后自动尝试融合,融合分高直接合并,融合分低创建新档案并展示
- 采集页维持现状
- 优点:用户体验流畅
- 缺点:误报可能污染数据

### 方案 C:混合(推荐)
- **走失上报(采集页 + owner 创建动物)**:走审核
- **普通发现(发现页 + 路人甲发现)**:不审核,自动融合
- 区分依据:`event_type` 或 `user_role`
- 优点:覆盖两种场景,符合"谁创建谁负责"原则

## 验收标准

- [ ] 两种入口处理流程有明确文档
- [ ] 融合算法统一(参见 BUG-006)
- [ ] admin 审核端支持两种来源的事件
- [ ] 用户原话里提的"鼻纹相似度算法应统一"落地
